# Claims And Limitations Matrix

| Topic | Safe manuscript claim | Repository evidence | Suggested wording | What not to say | Limitation | Future-work phrasing |
|---|---|---|---|---|---|---|
| Flask web application | V-LiSEMOD is implemented as a Flask web app | `app.py`, templates, `Procfile` | “V-LiSEMOD is a Flask-based web platform.” | “enterprise web platform” | Route-heavy single-app structure; limited formal tests | “Future work can modularize and test additional route groups.” |
| Public no-login workflow | Main scientific workflows are accessible without login in the current app | No active auth flow in `app.py`; disabled `users.db` references in docs | “The current public workflow is no-login by default.” | “fully access-controlled public portal” | Security controls for anonymous use are limited | “Authentication can be added later if deployment needs change.” |
| Structure explorer | App supports virus -> PDB -> ligand exploration and export-oriented review | `/`, `/generate_ligand_images`, `/generate_pymol_session` routes | “The Structure Explorer supports structure-specific ligand review.” | “automated structure design engine” | Depends on provisioned database and writable outputs | “Future work can add fixture-based demos and richer provenance.” |
| Virus/PDB/ligand selection | Users can navigate curated virus, PDB, and ligand choices | lookup routes in `app.py` | “Users can select curated virus, structure, and ligand contexts.” | “complete viral structure universe” | Coverage depends on current curation | “Coverage can expand as additional curated records are added.” |
| PyMOL-oriented export | App can generate PyMOL-oriented session artifacts | `/generate_pymol_session`, `pml_sessions/` | “The app supports PyMOL-oriented export workflows.” | “full structural modeling suite” | Output generation depends on writable filesystem and local assets | “Future work can add more portable export packaging.” |
| Ligand image generation | App can generate ligand imagery for selected contexts | `/generate_ligand_images`, static cache folders | “Ligand imagery can be generated from selected structural contexts.” | “publication-grade structure rendering pipeline” | Generated images depend on runtime caches and source tables | “Future work can standardize figure-ready rendering outputs.” |
| Binding-pocket export | Binding-pocket context can be assembled when data are available | `receptor_binding_pocket` usage | “Binding-pocket context is available for selected workflows.” | “full pocket-detection engine” | Depends on existing prepared data layers | “Future work can expose pocket-generation provenance more explicitly.” |
| SASA / solvent-exposed atom review | App presents SASA-derived exposed-atom cues | `RUPLEY_SASA_DATA`, solvent-exposed routes | “V-LiSEMOD integrates SASA-derived solvent-exposure evidence.” | “proves modifiability” | Exposure is suggestive, not definitive chemistry proof | “Future work can benchmark exposure cues against design outcomes.” |
| Functional-group annotations | Functional-group context is available for interpretation | `Functional_GROUPED`, `Functional_Group_Atoms` | “Functional-group annotations provide ligand-context interpretation.” | “automated synthetic route planning” | Annotation quality depends on upstream mapping | “Future work can expand and validate annotation coverage.” |
| Protein Query | App supports target-centric filtering and export assembly | `/query_protein_virus_page`, related routes | “Protein Query supports target-centric structural retrieval.” | “complete viral target knowledgebase” | Depends on curated contents of the current data layer | “Future work can extend target coverage and filtering metadata.” |
| Ligand Indexer | App supports ligand-first mapped-context lookup | `/ligand_indexer` and related routes | “Ligand Indexer supports ligand-first structural lookup.” | “global ligand intelligence engine” | Limited to curated mapped contexts | “Future work can broaden ligand normalization and synonym coverage.” |
| Ligand Comparison | App supports cross-structure comparison of selected ligands | `/compare_ligands`, comparison routes | “Ligand Comparison supports cross-structure interaction review.” | “validated SAR engine” | Comparison quality depends on mapping and source structures | “Future work can add fixture-backed benchmarking and summary metrics.” |
| Interaction charts | App can generate chart-style interaction summaries | `generate_charts`, `Arpeggio_Contacts_Data` | “Interaction charts summarize ligand contact context.” | “complete interaction energetics model” | Contact layers are descriptive rather than biophysical simulations | “Future work can add clearer chart provenance and export fixtures.” |
| PROTACability assessment | App exposes transparent heuristic PROTACability views | `/protacability_page` and API routes | “PROTACability outputs support transparent design triage.” | “predicts degradation” | Heuristic evidence only | “Future work can benchmark heuristic layers against case studies.” |
| Warhead linkability | App captures ligand-centered linker-attachment cues | `protacability_warhead_linkability` | “Warhead linkability highlights ligand-centered attachment opportunity.” | “identifies optimal linker atom with certainty” | Dependent on mapping and heuristic scoring | “Future work can compare these cues with medicinal chemistry outcomes.” |
| Target lysine accessibility | App captures exposed lysine proximity cues | `protacability_lysine_proximity` | “Target-side lysine accessibility is presented as a structural cue.” | “predicts ubiquitination” | Accessibility does not prove productive biology | “Future work can incorporate richer target-side context.” |
| Degrader-readiness heuristic | App aggregates heuristic degrader-readiness signals | `protacability_degrader_readiness` | “Combined readiness layers provide degrader-oriented triage.” | “validated degrader-readiness score” | Not a ternary-complex or degradation predictor | “Future work can test heuristics against curated examples.” |
| PROTAC Builder handoff | App links users to downstream companion-tool workflows | external URL and compatibility routes | “V-LiSEMOD supports handoff to PROTAC Builder.” | “contains a full in-repo PROTAC builder” | Companion tool is external to this repo | “Future work can strengthen structured handoff metadata.” |
| Warhead Hunter ecosystem connection | App is positioned within a related companion-tool ecosystem | README, templates, footer links | “V-LiSEMOD sits alongside related structure-guided tools such as Warhead Hunter.” | “fully integrated shared platform” | Integration is conceptual and link-based unless otherwise documented | “Future work can expand explicit cross-tool interoperability.” |
| E3 Ligandalyzer ecosystem connection | App references E3 Ligandalyzer as a related tool | README, templates, RANDY E3 routes in repo | “The project is framed within a broader companion-tool ecosystem that includes E3 Ligandalyzer.” | “V-LiSEMOD includes full E3 Ligandalyzer functionality” | Same-ecosystem framing does not equal identical app scope | “Future work can define clearer interoperability surfaces.” |
| Optional Drug GPT / BioGPT module | Assistant module is optional and deployment-dependent | `DRUGapp.py`, feature flags | “An optional local assistant module can be enabled in selected deployments.” | “AI assistant is always available” | Requires extra dependencies, tokens, and model runtime | “Future work can clarify supported assistant modes and fixtures.” |
| Local SQLite backend | App can run directly from local SQLite data | `viral_data.db` usage throughout `app.py` | “Local SQLite-backed workflows are supported.” | “self-contained public dataset included in repo” | Database is provisioned separately and should stay out of public Git | “Future work can add redacted demo fixtures.” |
| RANDY-backed remote mode | Selected workflows can use RANDY-backed data routes | backend helpers in `app.py`, `RANDY/` | “Selected route groups can run against a RANDY-backed data service.” | “all deployments use the same hosted backend” | Environment-specific and deployment-dependent | “Future work can formalize backend compatibility tests.” |
| Generated caches and outputs | App generates caches, images, sessions, and exports at runtime | cache folders and routes | “Several outputs are generated at runtime.” | “all outputs are stored as canonical source artifacts” | Generated folders require write access and should not be versioned | “Future work can improve output packaging and cleanup automation.” |
| Local or provisioned data requirements | App depends on provisioned scientific data | local DB and generated-folder assumptions | “V-LiSEMOD depends on local or provisioned data assets.” | “works out of the box with no data provisioning” | Repo alone is not a complete runnable dataset | “Future work can ship minimal redacted fixtures.” |
| Hosted deployment | Flask app can be deployed with configured runtime assets | `Procfile`, docs, `/healthz` | “The app is deployable as a Flask service with provisioned assets.” | “production-hardened hosted platform” | Durable storage, scalability, and ops guarantees are not established here | “Future work can document hardened deployment patterns.” |
| Public GitHub source availability | Source and docs are being prepared for public release | README, docs, `.gitignore` work | “The repository is being prepared for public GitHub sharing.” | “all local research assets are public” | Data and generated artifacts remain separate | “Future work can add curated sample data and release tags.” |
| Manuscript reproducibility | Repo can support reproducibility planning | docs/manuscript materials | “The repository includes reproducibility planning guidance.” | “fully reproducible from public repo alone” | Scientific data and environment provisioning are still external | “Future work can add pinned fixtures and scripted smoke tests.” |
| Experimental validation | No experimental degradation validation is shown here | absence of validation evidence in repo | “The current repository supports hypothesis generation rather than experimental validation.” | “experimentally confirmed degradation” | No wet-lab evidence in inspected materials | “Future work can pair software with validated case studies.” |
| Benchmarking | Benchmarking is not yet established in the inspected repo | no benchmarking framework observed | “Benchmarking remains future work.” | “benchmarked predictive tool” | No validated benchmark set documented | “Future work can define benchmark tasks and evaluation criteria.” |
| Production readiness | Research-oriented deployment is supported | app and docs inspection | “The app supports research-oriented deployment.” | “fully production-ready platform” | Testing, hardening, and ops evidence are limited | “Future work can formalize deployment and monitoring standards.” |
| Authentication and security | Current public workflow is no-login by default | active route behavior and docs | “The current scientific workflow is no-login by default.” | “robust auth and rate-limiting are implemented” | Auth, rate limiting, and security controls are not a present-tense feature claim | “Future work can add optional access control for hosted deployments.” |
